# Engineering Constraints

本文档是 Nexus Terminal 仓库**唯一权威的工程约束登记表**。它位于 software-requirements 目录下，使软件需求、架构文档、测试文档、实现工作与当前 Agent 演进都能引用同一组稳定的 `EC-*` 约束编号。

Software requirements may define product capabilities, observable behavior, quality goals, and design requirements. They must not restate a mandatory engineering rule as a second normative source; they reference the applicable `EC-*` entry here.

## Constraint change process

- Add or change mandatory engineering rules only in this register.
- If a new instruction conflicts with an existing constraint, report the conflict instead of silently replacing either rule.
- Once the project owner resolves the conflict, update this register before treating the decision as established project policy.
- Implementation details that are not intended to constrain future work stay in the owning architecture/feature document.

## Authority and conflict protocol

| Provenance  | Meaning                                                                                                                                                                             | Change / conflict policy                                                                                                                                                                                                                                                                                                                                                                                                |
| ----------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **OWNER**   | Direct project-owner instruction or an owner-confirmed project decision.                                                                                                            | **Owner-locked.** Agents must enforce it as written. A later instruction that conflicts with an existing `OWNER` row must not silently replace, weaken, reinterpret, or scope it away. The agent must identify the conflicting `EC-*` rows and ask the project owner to choose whether to keep the historical rule, replace it, merge the rules, or narrow their scopes. The register changes only after that decision. |
| **DERIVED** | Constraint synthesized from repository architecture, implementation history, existing documentation, or engineering analysis rather than a directly attributable owner instruction. | Mandatory while present in this register, but it may be revised when repository evidence/design changes. A `DERIVED` rule can never override an `OWNER` rule; conflicts escalate to the project owner.                                                                                                                                                                                                                  |

## OWNER provenance notes

`OWNER` is intentionally limited to rules that can be attributed to a direct project-owner instruction/decision in the project history. The current OWNER set includes project-owner decisions covering ES2025, frontend ownership and capability boundaries, clean camelCase contracts, Workspace/Agent runtime isolation, AI development instructions, standard repository checks, real product assertion surfaces, guarded E2E diagnostics without test-only DOM seams, E2E-owned screenshot checkpoints, the single-source/provenance conflict protocol, documentation ownership under `doc/`, and Docker helper-script ownership under `scripts/docker/`.

If later evidence suggests a `DERIVED` row was also a direct owner decision, it may be promoted to `OWNER` only with owner confirmation. This avoids falsely attributing repository-derived rules to the owner.
