# Frontend UI Restoration Plan

Status: **owner-approved restoration plan; implementation not started by this document change**  
Primary source-code baseline: Git commit [`8ceb5840`](https://github.com/0honus0/nexus-terminal/commit/8ceb5840)  
Supplemental visual baseline: screenshots stored at Git commit [`8ad24a03`](https://github.com/0honus0/nexus-terminal/commit/8ad24a03) before the manifestless screenshot refresh  
Current architecture target: `packages/frontend/src/app`, `features`, `runtimes`, `foundation`, `shared`  
Governing constraints: [EC-FE-001](software-requirements/engineering-constraints.md#ec-fe-001), [EC-FE-002](software-requirements/engineering-constraints.md#ec-fe-002), [EC-E2E-001](software-requirements/engineering-constraints.md#ec-e2e-001), [EC-E2E-002](software-requirements/engineering-constraints.md#ec-e2e-002), [EC-GEN-002](software-requirements/engineering-constraints.md#ec-gen-002).

## 1. Goal and scope

Restore the **entire established frontend UI**, not only the 28 surfaces that currently have functional screenshots. The runtime refactor is retained: UI parity is restored **on top of the new architecture**, and the deleted legacy component/store/event-bus architecture is not recreated.

The audit scope is the complete pre-runtime-migration frontend at `8ceb5840`:

- **224** tracked files under `packages/frontend`, including **212** under `packages/frontend/src` plus package/public/config files.
- The current package has **354** tracked files, including **340** under `packages/frontend/src`.
- **98** Vue UI files to review one by one.
- Old UI topology centered on **84 `components/` files** and **13 `views/` files**.
- Global visual sources: `style.css`, `features/appearance/config/default-themes.ts`, `features/appearance/config/iterm-themes.ts`, application shell, assets and FontAwesome usage.
- Current frontend has **340** source files and **94** Vue files, split into feature/runtime/foundation owners. A missing one-to-one Git rename is **not** evidence that visual behavior was intentionally changed.

Functional screenshots are evidence, not the scope definition. UI without a screenshot is restored from the old template/style/icon code and the old interaction behavior.

## 2. Restoration rules

1. **Old visual behavior, new ownership.** Copy visual semantics—DOM composition where still appropriate, classes, dimensions, icon choices, responsive rules, state styling and interaction presentation—into the current owner. Do not copy old stores, event bus, transport coupling or internal compatibility code.
2. **No PNG substitution.** Old screenshots are comparison evidence only. Never copy old images over newly generated screenshots to hide a product regression.
3. **No feature regression for visual parity.** Current clean HTTP/WebSocket/runtime behavior stays intact. If old visual code is coupled to removed architecture, reproduce its presentation through current props/composables/capability surfaces.
4. **No screenshot-only fixes.** A file is restored even when no screenshot checkpoint covers it. Screenshots are added only where a real E2E scenario benefits from a durable documentation checkpoint.
5. **Shared cause before local patch.** Fix global tokens, icon loading, Base UI primitives, terminal fallback and modal/overlay geometry before adding component-local overrides.
6. **Desktop and mobile are separate parity targets.** Old mobile-specific classes, touch controls, viewport behavior, popup/fullscreen behavior and virtual-keyboard layout are reviewed explicitly.
7. **Intentional differences require owner decision.** If the current requirement genuinely conflicts with the old UI, record the old behavior, current requirement/constraint ID and proposed divergence; do not silently keep the new design.

## 3. What must be compared for every old UI file

Each row in the inventory below is not complete until the implementation review records all applicable items:

- DOM/layout topology: container hierarchy, flex/grid direction, ordering, pane/modal composition.
- Geometry: width/height/min/max constraints, padding, margins, gaps, row density, splitter sizes.
- Typography: font family/size/weight/line-height, monospace use, truncation/wrapping.
- Theme/color: backgrounds, foregrounds, borders, active/hover/focus/disabled/error/success states.
- Icons: exact semantic icon, icon library, size, alignment, color and hover state. Unicode substitutes are not accepted when the old UI used a real icon unless explicitly approved.
- Controls: button variants, input/select sizing, checkbox/toggle layout, loading indicators, disabled appearance.
- Layering: modal/backdrop/z-index, popup anchoring, context menu/submenu placement, non-blocking overlays.
- Overflow: scroll container ownership, scrollbar dimensions, sticky headers/toolbars/tabs, horizontal-scroll behavior.
- Responsive/mobile: breakpoints, touch target size, full-screen overlays, compact controls, keyboard-safe layout.
- Dynamic states: empty/loading/error/connected/disconnected/active/dirty/progress/queued/cancelled states.
- Accessibility-visible parity: labels/tooltips remain accessible while restoring the old visual design.

## 4. Baseline findings that must be fixed early

The initial repository scan already found shared regressions that affect many files:

- **Terminal theme fallback regression:** the old appearance store fell back to `#1e1e1e` / `#d4d4d4` terminal styling when no active theme was resolved. The current Workspace theme computation can return `undefined`, allowing xterm's black/white defaults. This affects desktop and mobile terminal screenshots and any terminal-derived surface.
- **Icon regression:** FontAwesome remains installed, but the old `src/main.ts` imported `@fortawesome/fontawesome-free/css/all.min.css` while current `app/main.ts` does not. Many new components also use Unicode glyphs such as `×`, `↻`, `⌕`, `↑`, `↓`, and `◐` where the old UI used semantic FontAwesome/SVG icons. Restore the global icon stylesheet through the current app bootstrap and restore semantic icons at current owners rather than creating a new legacy icon layer.
- **Global CSS loss:** old `style.css` included global icon color/hover behavior, input disabled/focus styling, primary-button icon color, button focus behavior and splitpane styling that are absent or reduced in current `global.css`. Re-establish only still-applicable global rules; keep component-specific rules local.
- **Component decomposition drift:** the old 98 Vue files became 94 current Vue files with many delete+add migrations rather than renames. Functionality passing E2E therefore does not prove template/style parity.
- **Embedded-view topology:** `CommandHistoryView`, `QuickCommandsView` and `SuspendedSshSessionsView` were embedded in old `LayoutRenderer`/modals rather than top-level routes. Restore their embedded presentation in current Workspace owners; do not invent routes merely because the old files existed. `TagsView` was not an active route at the baseline and requires usage verification before any surface is added.

## 11. Validation gates per restoration batch

Each batch must remain small enough to attribute visual changes to current owners.

1. `npm run format` and `npm run format:check` for changed files.
2. `npm run check:test-policy`.
3. Frontend build and architecture guard.
4. Relevant existing E2E specs; add/adjust E2E only for real user-visible behavior, never internal component assertions.
5. For screenshot-covered surfaces, run the real screenshot scenario and compare to the old image.
6. For mobile-affecting components, run at least the relevant mobile E2E project before closing the batch.
7. Full canonical GitHub Actions G1–G8 before declaring a phase complete.
8. At major visual milestones, manually dispatch the functional screenshot workflow and review **all generated images**, not only files changed by that batch.

## 12. Commit strategy

Do not restore all UI in one commit. Suggested sequence:

1. `fix(ui): restore global visual foundation`
2. `fix(ui): restore app shell and common controls`
3. `fix(ui): restore management and settings surfaces`
4. `fix(ui): restore workspace layout and controls`
5. `fix(ui): restore terminal and mobile keyboard visuals`
6. `fix(ui): restore file manager and editor visuals`
7. `fix(ui): restore preview visuals`
8. `fix(ui): restore transfer and progress visuals`
9. `fix(ui): restore auxiliary workspace surfaces`
10. final parity cleanup only after full screenshot/manual review.

Every commit must preserve current architecture and product behavior. If a visual restoration needs a state/event behavior that only existed through a deleted mega-store/event bus, stop and implement the equivalent through the current feature/runtime public surface rather than reviving the old mechanism.

## 13. Definition of done

UI restoration is complete only when:

- all **98** old Vue files have a closed audit row with evidence of parity, replacement, or an owner-approved intentional difference;
- global styles/themes/assets/icon semantics have been audited;
- all current active routes and embedded Workspace surfaces match the established baseline;
- desktop and mobile layouts have both been reviewed, including UI with no screenshot checkpoint;
- the 28 current screenshot checkpoints have been regenerated from real E2E and reviewed against the pre-refresh baseline;
- no old component directory, mega-store, global event bus, legacy protocol mapper or compatibility facade was reintroduced;
- current SRS functionality remains intact;
- format, test-policy, Frontend build, architecture guard and canonical G1–G8 pass;
- any intentional visual difference is explicitly approved by the project owner and recorded against the relevant old file/current owner.
