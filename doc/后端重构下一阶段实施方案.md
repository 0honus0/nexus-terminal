# 后端重构下一阶段实施方案

## 本阶段目标与使用方式

下一阶段是 **HTTP/WebSocket 协议边界整理与真实消费者同步迁移**。现有新后端已提供有限的 Access、Targets、Remote、Agent 路由，本阶段在这些实现上收口契约、解码、错误映射和资源生命周期，不重新搭建后端。P0 已完成首轮真实端点与消费者盘点（见下表），P1 已开始技术边界施工；其它事项只有在代码、消费方及检查同步完成后才逐项标记。静态检查不等于行为验收。

长期约束统一遵守 [AGENTS.md](AGENTS.md) 与[架构重构](架构重构.md)，尤其是[全局编码约定](架构重构.md#全局编码约定)、[模块出口约束](架构重构.md#全局模块出口约束)、[HTTP/WebSocket 接入与协议长期约束](架构重构.md#httpwebsocket-接入与协议长期约束)。实际 owner 与调用关系同步维护 [Backend 架构](architecture/BACKEND.md)、[Frontend 架构](architecture/FRONTEND.md)；历史专项证据和未通过项统一放在[验收文档](testing/E2E.md)，本文不保留旧 A–D 审核报告或执行阶段施工清单。

实施顺序为 P0 → P1 → P2 → P3 → P4 → P5。P2–P4 可按 Access、Targets、Remote 的完整功能逐项推进，每项同时修改所有真实消费者；不一次铺满空类型、空客户端或空接口目录。每个独立事项完成后同步文档、检查并本地提交，推送按用户指令进行。

## P0：盘点端点、协议与消费者

**目的：先确认真正需要调整的契约及其 owner，避免由类型名称推测行为。**

逐条读取现有路由、Shared、前端调用与旧正式消费者，为本阶段端点建立契约表。每条记录包含：method/path、path/query/header/body、成功与业务失败形状、HTTP 状态码、鉴权与资源归属、敏感字段、版本/幂等、输入上限、公开消费者，以及未接入功能。契约表在本文对应批次就地维护，收口后将长期约束移入正式架构文档，不另建长期接口进度台账。

必须盘点：

- Access 的 `needs-setup/setup/login/status/logout/password`：初始管理员、未认证结果、登录轮换、注销/密码变更撤销、rememberMe 与 cookie 设置/清除；确认开发页所有内联 fetch 消费者。
- Targets 的 Connection/Proxy/SSH Key/Tag 管理，Connection clone、关联 Tag、导入、凭据变更/删除，以及 Host Key list/confirm/remove；区分管理结果与后端可信 SSH 解析，确认后者从不进入公开 HTTP。
- Remote 的 `POST /sessions`、`GET/DELETE /sessions/:id` 和 `/stream?sessionId`；列出每种客户端/服务端事件、合法次序、owner/token 绑定、正常与异常退出结果。
- Agent 的 App/Thread 创建、Run 创建/查询/取消、事件分页；记录 Idempotency-Key、expectedVersion、scope、replayed/originalStatus 和 cursor 语义。当前 Run 仍限 pending/cancelled，无前端消费者的类型留在模块内。
- Shared 的已有 `connections/proxies/ssh-keys/tags/targets/remote` 契约及精确 exports；检查是否遗漏真实双端类型、重复定义或只靠类型断言的解析。

**完成判据：** 所有范围内端点都能追到生产代码的输入解码、用例、输出映射和实际消费者；需要更改的协议有明确理由、受影响方和迁移办法。旧生产消费者只用于发现遗漏，不据此扩大到完整产品迁移。

| ------- | ----------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------- |

## P1：收口通用 HTTP/WS 技术能力

**主要位置：** `platform/http`、模块 `register.ts` 和 Bootstrap 的安装/关闭入口。

1. 按 P0 结果确认通用 route/context/channel 的最小能力：原始参数、`unknown` JSON、响应发送、cookie、来源信息、AbortSignal 与关闭责任。若契约和技术实现确实需要独立演进再拆文件；不为目录对称增加空转包装。
2. Platform 负责监听、匹配、JSON/Content-Type/body 上限、Origin/Fetch Metadata、受信代理与技术输入错误。业务 route 负责自己的 query、分页、header、权限和状态语义。保留非法 JSON 400、过大 body 413、不支持媒体类型 415，不让模块 catch 改为 500/503。
3. 复核路由重名/冲突、响应是否已结束、异步失败和 WS upgrade 拒绝路径；错误后不能二次发送或遗留未处理 Promise。只补充真实安装所需的通用检查，不引入业务路由注册槽位、万能 RPC 或全局业务分发器。
4. 保留 WS 有序消息处理与累计上限，发送背压、finish 和强制 close 的责任明确。Platform 不读取 Remote/Agent frame，不持有 Session/Run 状态。
5. 关闭停止准入，等待 HTTP 任务、升级鉴权和 WS 已接纳任务；模块完成建连/会话清理后才关闭 SQLite。浏览器断开不能被当成密码验证/已开始事务已取消，失败仍继续必要释放并聚合。

**完成判据：** Access、Targets、Remote、Agent 均只依赖通用技术契约；Bootstrap 只安装模块提供的能力和编排生命周期。技术 4xx、安全检查、队列上限和停机等待没有退化。Platform 不导入业务 DTO/状态，也不制造无人使用的抽象。

**P1 第一项完成**：`http-server.ts` 已对等价参数模板做启动期拒绝，对已发头/无响应的异步 handler 防止二次状态码及悬挂请求，JSON 序列化在发送响应头前完成；P1 其余 Origin/代理、shutdown/WS upgrade 失败窗口还需独立复核。未运行新行为测试，保留 P5 待验收清单。

## P2：补齐 Shared 与边界校验

**主要位置：** `packages/shared/src`、`packages/shared/package.json` 以及真正消费这些契约的两端。

### 目录和依赖

- 保留现有按域结构。`values.ts` 仅放双端基础取值；`model.ts` 放同义同表示业务对象；`api.ts` 放请求/响应、结果与对应纯边界校验；`events.ts` 放事件及校验。按现有约定使用精确子路径 exports，不加根 barrel 或通配符。
- Access 已有真实前端认证消费者，新增 `access/api.ts`；仅有真实需要时补充 `model.ts/values.ts`。身份/授权内部上下文、会话摘要、scrypt/密文等不共享。认证密码可以作为必要的写入输入，绝不进入响应、事件或错误。
- 在已有 Connections/Proxies/SSH Keys/Tags/Targets/Remote 域内补缺，不另建包罗全部业务的 `protocol.ts`。Agent 无对应新前端消费者，暂不建立 Shared agent 空域；将来消费者接入时逐项迁移。
- 校验不依赖 Node、Vue、HTTP 框架或 SQLite。大规模校验确需独立文件时，说明其唯一 owner、精确导出及单向依赖，保持 `values` 无同域业务依赖，避免 api/model/codec 相互循环。

### 契约要求

1. 明确 JSON 表示、必填/可选、未知字段、重复参数、长度/字节/集合上限和 number 范围；枚举及状态用具名类型与可辨识联合，不以一个 status 类型加大量可选字段代替。
2. 更新请求保持 `{version, changes}`：省略/undefined 不修改，null 仅对可清除字段有效，具体值表示设置；明确不允许客户端控制的字段。JS undefined 不作为 JSON wire 值。
3. 从 unknown 解码到契约对象，嵌套结构同样校验。同表示规则在双端共用；权限、Host Key 信任、业务引用、事务及存储不变量仍归后端模块，不迁 Shared。
4. 成功响应按实际端点语义定义，不无端统一包成 `{data: ...}`。明确空响应/无正文与 JSON 的区别；稳定技术错误和域错误各有 owner，不合成全局大状态枚举。未知错误码仍作为失败处理，UI 显示安全兜底文本。
5. 公开结果禁止密文、私钥、会话摘要、SQL 行和内部事务。协议版本按真实变化决定，API v1 与业务记录 version/CAS 是不同概念；不能为未实现的 Agent wire 预设假版本或兼容框架。

**完成判据：** 每项新增 Shared 契约有真实的前后端消费者；同义重复类型/校验被替换，精确 exports、依赖及两端构建同步。敏感写入与公开读出字段有明确区别，内部类型未被提升为共享大集合。

## P3：按模块接入协议与安全映射

**主要位置：** 各模块 `interfaces/http`、public 契约与出口 mapper。

通用调用链为：技术请求 → 模块协议解码/鉴权 → 模块公开输入 → Service/Model → 模块公开结果 → 协议响应。协议 helper 只处理接入问题，不直接调用 Storage/SQLite，不复制 Service 业务规则。

### Access

将 P2 的认证契约用于现有六类路由，逐项定义 needsSetup、登录/身份状态、未认证状态、注销与密码变更结果；返回只包含公开身份字段。保留 cookie 的 HttpOnly/SameSite/部署 Secure 设置及清除路径、固定 Origin 策略和当前管理员限制。登录因素未迁移时明确拒绝，不能悄悄绕过。业务错误由 Access 映射，通用 HTTP 输入错误继续交由 Platform。

### Targets

补齐管理输入/响应与 Host Key 的解码/编码。CAS 更新、版本冲突、引用占用、缺失对象、凭据操作、clone、关联 Tag 和按条导入结果必须逐个保留语义；导入上限 50 条、按条事务和部分成功不改成批量假原子。确认 Host Key 使用可信核对后的 SHA256，不默认信任；只暴露允许的端点/指纹管理信息，可信明文解析仍是后端专用出口。

模块 public 白名单与 Model 存储转换保持分工：前者限制出口字段，后者转换应用和持久表示。不能把 `connection-mapper.ts` 搬入 public mapper，也不能因 Shared 字段相同直接返回内部对象。

### Remote

Session HTTP 的创建/查询/释放结果与 WS frame 使用真实契约；校验 sessionId、frame 类型/长度、base64、resize 和 consumed 字节。明确 ready/data/drain/blocked/closed/error 的合法状态，未知消息或超额 ACK 不继续执行。HTTP 与 WS upgrade 均从 Access 获取身份并检查 owner/token；Access 撤销与来源失败不能退化为匿名接入。

保留当前限额与关闭语义，详见[Backend 架构 Remote 章节](architecture/BACKEND.md#backend-next-remote-httpws-与-ssh-host-key-信任)：正常 EOF 尾字节等待渲染 ACK，再 closed/正常握手；SSH 断线/清理失败返回安全错误；主动关闭/撤销/停机有独立路径。最近释放缓存只在读取时清过期项，插入后超容量才淘汰；它只确认有限窗口内相同 token 的释放结果，不承担恢复或持久幂等。

### Agent

仅整理当前后端私有契约、输入解码和公开结果。userId 由服务端身份取得；App/Thread/Run 归属、Idempotency-Key、expectedVersion、事件 after/limit 均有界验证。保留首提交冻结结果的 replayed/originalStatus、创建/取消/冲突的独立联合与最多 100 条事件页；公开视图不包含输入原文、请求 hash 或内部 userId。commit_unknown 仍是安全不可用，不通过 HTTP 自动重放未知写入。不扩大 Run 状态或开放假执行入口。

**完成判据：** 每条端点具备明确输入、公开字段、安全错误/状态码与权限边界；所有联合分支完整处理，不默认为某个现有状态。没有技术原始异常泄露、通用 4xx 被吞、重复对象定义或 Storage 越界调用。

## P4：同步真实前端 API 与 Transport

**主要位置：** `features/targets-next/api`、`features/targets-next/views/TargetsNextDevView.vue`、`runtimes/remote-next/transport` 及对应 i18n。

1. 将开发页内联 Access fetch 和认证响应处理移到明确的 API owner，View 只执行公开操作、管理展示状态。Access 语义不同于 Targets 管理，不塞入连接 CRUD 客户端；存在独立跨功能消费时再建立相应 Feature 公开入口。
2. Targets API、Access API 和 Remote Transport 分别消费 Shared 请求/响应/事件解码。HTTP JSON 与 WS JSON 均先按 unknown 处理，不能用 `as DTO` 代替验证；未成功响应不能按成功对象解析。
3. 抽取通用 fetch 前确认实际重复的网络语义、错误与取消责任。若 Access/Targets/Remote 确实共用，在现有 Frontend foundation 的适当 owner 提供最小技术请求能力，通过公开入口消费；否则保留局部 helper。不依赖旧 Agent 业务 HTTP client，不建立巨型客户端框架。
4. 处理非 JSON/空正文/网络失败、稳定错误码与 AbortSignal；业务 payload 解码归对应 API/Transport。提交未知或幂等操作不能由通用客户端自动重试；同一操作重试沿用原键和语义参数。
5. 保留 Remote Socket、frame、ACK、generation 和共享 close Promise 的 Transport owner。组件不接管 wire，不复制服务端 Session 状态；渲染完成才 ACK，旧连接迟到错误不覆盖新连接，晚到成功/卸载仍释放资源。DELETE 未确认或关闭失败必须可见。
6. 用户文本同步现有 `i18n` 的 en-US/zh-CN/ja-JP，移除失效 key；不新增 `locales` 目录或显示原始技术异常。隔离开发页 `/__targets-next` 继续通过显式 `NEXUS_VITE_BACKEND_NEXT_ORIGIN` 配置的 `/__next` 代理接入，不影响正式登录态/Store/Workspace。
