# 后端重构下一阶段实施方案

## 起点与待收口事项

第一版的代码范围已实现：独立 `backend-next` 与 `shared`；应用实例独占的 SQLite Worker、参数绑定、显式排他事务、关闭与故障拒绝；Targets 内的 Connection Service → Model → 存储契约 → SQLite Adapter；连接元数据 CRUD、CAS、标签和跳板关系、跨 Proxy/Tag 的单条导入事务。`targets` 是当前唯一装配的业务顶层模块。旧 Backend 仍服务正式产品，新包不监听 HTTP，也不读取旧数据库。

第一版实施清单不再作为施工任务保留。**验收仍待收口**：本轮仅运行 `backend-next` TypeScript 检查并通过；用户要求暂不运行测试。现有 SQLite 集成脚本曾在 Runtime 最后一次改动前通过，不能代替当前版本的验证。恢复测试时，先重新执行该脚本，再覆盖 Runtime 的 Worker 异常退出、事务回调误用默认入口和过期事务句柄；这些检查完成后才能把第一版称为已验证，而不是只称代码范围已实现。

以下各阶段只定义下一批需要建设的能力；不为后续模块预建空目录、假接口或假的服务。`packages/shared` 随真正的双端消费者按域增量补齐，`packages/protocol` 在全部消费者切换后删除。重构期间两套 Backend 不互相调用，也不分流正式请求。

## 1. 先稳定数据库与应用实例底座

1. 将当前只识别版本 1 的 Schema 初始化扩展为**按编号、一次性、可恢复的迁移机制**。Platform 管版本、执行顺序和事务；每个业务模块拥有自己的 DDL/数据迁移内容。明确迁移失败后的数据库状态与启动拒绝规则，避免以后直接改 `CREATE TABLE IF NOT EXISTS` 来冒充升级。
2. 保持 `SqliteRuntime` 只提供通用 SQL 执行、显式事务、故障与关闭能力。Worker 失效后所有新调用明确失败；不自动重放提交结果未知的写入。事务参与者只能使用收到的 `tx`，不能在回调中调用默认入口、嵌套事务或等待网络/用户交互。
3. Bootstrap 逐步形成应用实例生命周期 owner：初始化数据库与模块，最后开放请求；停机或恢复时先停止接纳新工作，收敛 Agent/Remote 的运行资源，最后关闭数据库。此阶段只建立必需的生命周期接口，不实现备份恢复或全量模块注册。

## 2. 补全 Targets，使 SSH 目标真正可解析

1. 在 `targets` 内增加 Proxy、Tag、SSH Key 的真实管理用例及存储契约；引入凭据加解密能力和必要的 Schema 迁移。密文只进入后端存储，公开结果不得泄露；Proxy/Key/跳板的引用保护继续在写事务内复验。
2. 增加 SSH 目标解析和配置指纹：从连接定义、密钥、代理、显式跳板链生成一次连接所需的不可变配置；依赖变化必须改变指纹。RDP/VNC 的连接定义仍由 Targets 管，运行中的票据和会话归 Remote。
3. 首次接入连接 HTTP 时，同批迁移对应的前端模型、API 客户端及 `protocol` 消费者，补 `shared/connections|proxies|ssh-keys|tags` 中确实共用的 `values.ts`、`api.ts`。请求从 `unknown` 校验；旧 wire 的 `route: null` 与新内部的 `direct` 在 API 边界显式转换。认证接入之前不开放无保护的管理路由。

## 3. 建立供 SSH 应用与 Agent 共用的机器能力

Platform 提供业务无关的 SSH 连接工厂、Proxy/Jump 建连、命令通道、交互式 Shell、SFTP 文件句柄/流、取消、断连与资源关闭。其参数只描述机器连接和通道，不包含 Connection ID、Workspace ID、Agent Thread、grant 或审批类型。Targets 负责把业务配置转换为机器连接参数；Remote 和 Agent 分别决定何时建连、授权、保留及关闭自己的会话。

先用 Remote 的最小 SSH 终端会话纵向接入，确认断连、关闭、取消和终端输出资源的归属；再接入文件操作与 Transfer 的独立任务生命周期。Agent SSH 会话、后台 Job 复用机器能力，但其身份绑定、配置指纹复验、授权、未知结果和恢复规则留在 Agent。

## 4. 单独设计 Agent 持久状态提交后再迁移 Agent

Agent 模块内部按 Run/状态提交、会话与 Memory、Provider、Plugin、App Storage、协作及授权等真实 owner 定义存储契约；不在 Platform 添加 `agentRuns` 等业务槽位。第一批先完成 Run、审批、事件和幂等记录的一次原子提交，以及重启后的状态恢复，再扩展其他 Agent 能力。

当前 SQLite Platform 的 `transaction(tx)` 能承载事务内“读最新持久状态 → 判断 → 条件更新多表 → 提交”。Agent 模块应拥有状态决策和事务内存储参与者；SQLite Adapter 使用同一个显式 `tx` 执行 SQL，并在提交成功后才把事件交给 Agent 调度/通知。不能把一次状态转换拆成多个普通 CRUD 调用，也不能让 Model 直接拿到通用 `SqlExecutor`。若选择事务外预生成提交计划，必须额外证明 Run、Thread、App、审批、子任务及幂等记录的版本条件完整；当前不把该候选方案作为默认实施前提。

## 后续切换条件

继续按 Access、Remote、Agent、Preferences、Notifications、Audit、System 的功能 owner 迁移，并逐域完成前后端 Shared 类型收口。完整认证授权、SSH/RDP/VNC、Agent、文件传输、通知审计、备份恢复、旧数据处理和部署路径齐备后，才统一切换正式入口、移除旧 Backend 与 `protocol`。第一版存储切片通过自身验收不代表满足正式切换条件。
