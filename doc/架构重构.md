# 架构重构

本文记录前后端共享类型及 Backend 基础组件的整体重构设计。SQL 至 Targets 连接元数据的第一版代码范围已实现；待收口验证和后续施工见[后端重构下一阶段实施方案](后端重构下一阶段实施方案.md)。新后端采用独立包、应用实例作用域的 SQLite Runtime 与业务模块装配，不承诺兼容旧数据或旧导入格式。现行产品职责以 [Frontend 架构](architecture/FRONTEND.md) 和 [Backend 架构](architecture/BACKEND.md) 为准；实施时同步更新正式架构文档及适用的开发规则。

## 全局模块出口约束

以下规则适用于重构中的**所有 Backend 业务模块**，包括模块给 HTTP/WebSocket 接口层、其他业务模块、内部能力分发入口和 Bootstrap 提供的对象。目录中的 TypeScript `export` 仅表示本模块文件之间可以导入，不自动构成模块对外契约；只有模块明确列出的出口能力可以被外部消费者使用。Platform 可以提供应用实例作用域的通用注册/分发机制，但业务能力名称、输入、结果和授权语义由所属业务模块定义，Platform 不收纳业务类型。模块内的 Service、Model 和 Adapter 不为普通调用绕行全局分发器。

- **内部类型与出口类型分开。** `storage/` 的记录、存储命令、密文、事务句柄和 SQLite 行类型只在模块内部使用。模块对外契约不得从 `storage/` 导入、再导出或通过 `Pick`、`Omit` 等类型运算派生内部记录；管理输入、公开视图和变更结果由业务模块按消费语义独立定义。即使当前字段完全相同，也维持这个边界。
- **所有对象越过模块出口时显式转换。** 输入进入模块用例、结果离开模块时逐字段构造新对象；列表逐项转换，嵌套对象与数组也逐层新建。创建、更新、删除、导入的结果及状态联合类型同样适用。不得直接返回内部 Service/Model/Storage 对象、使用对象展开复制内部记录，或用 `as PublicType` 冒充运行时转换。布尔值等基础值可以直接返回。
- **出口采用允许字段清单。** 转换函数只写明允许通过的字段。新增内部字段后，未主动修改出口契约和转换函数就不会自动流出。TypeScript 返回类型、`Readonly` 或 `Object.freeze` 不能删除运行时对象的额外字段，也不能代替显式投影；HTTP/WebSocket 响应在协议边界还需按 DTO 校验和序列化。
- **按调用方分开能力。** 管理操作仅交给所属模块的接口层或明确授权的管理消费者；其他模块只取得完成其用例所需的窄能力。含明文凭据或其他敏感资料的可信能力必须有独立出口、明确消费者和生命周期，不并入普通管理接口，也不挂载为公开 HTTP/WebSocket 响应。可信出口返回的目标、认证、代理、跳板等对象仍要逐字段构造，只包含该可信契约允许的字段。
- **变更字段语义明确。** 对补丁输入分别定义 `undefined`（不修改）、`null`（清除）和具体值（设置）的含义；明文变更输入与密文存储命令使用不同类型并在模块内转换。不能把存储字段直接开放为用户可写字段，也不能仅靠类型隐藏敏感值，必须由运行时出口转换和授权控制实际对象。

Targets 的 `ProxyManagement`、Tag/SSH Key 管理与连接 CRUD 可供 Targets 自己的管理接口层使用；Agent/Remote 只获取目标解析、指纹等必要的可信能力。第二批已调整 `targets/public.ts`：管理输入、返回视图和状态联合类型独立于 `storage/` 定义，`targets/public-mappers.ts` 逐字段投影所有输入及输出，`registerTargets` 不再返回内部 Service 实例或记录。可信 `trustedSshTargets` 继续从 Bootstrap 独立提供，并把认证、Proxy、有序跳板逐层映射为新对象。未来 HTTP 接入前仍必须完成真实认证、授权和 DTO 运行时校验。

## 基础组件整体重构（待实施）

本次调整覆盖 Backend 所有基础能力及其消费者，SQL 只是第一个样板。逐个能力迁移，最终让同一类调用遵循一致的依赖方向；不保留新旧入口长期并行。先盘点所有模块对数据库、SSH、文件系统、加密、网络与外部运行时的直接依赖，再按下表逐项替换。

重构以正常运行的产品结果和 `doc/USAGE.md` 的现行需求为验收基准；旧实现偶然形成的错误文案、异常处理和未发布兼容分支不机械保留。历史提交或现行需求明确指定的语义须保留，具体实现手段可以替换。

### 统一职责与依赖方向

```text
业务 Service → 本模块 Model → 本模块存储契约 → 本模块 SQLite Adapter
业务 Model ──────────→ Platform 通用机器能力契约 → 技术 Adapter
                                 ↑                    ↑
                           Bootstrap 安装实例并管理生命周期
```

- **Bootstrap** 读取配置、创建需要共享的运行时与具体 Adapter、安装能力入口、控制初始化和关闭顺序。它不做业务格式转换、SQL、SSH 或网络操作，也不集中构造所有业务模块的存储依赖。全局调整不表示所有对象都是全局单例：连接、会话、事务、Run 和操作句柄仍由各自 owner 创建与关闭。
- **业务模块 Model** 是该模块到存储或通用技术能力的入口，负责把应用对象与任务转换为所属契约所需的命令，并把结果校验、转换回应用对象；可薄封装一次能力调用。授权、业务规则与用例顺序仍由 Service 或其领域 owner 负责。模块之间调用业务能力应走所属模块的公开入口，不借基础组件跨越业务边界。
- **Platform** 只按通用机器能力定义接口、内部命令与结果、错误语义和生命周期约束，既不导入业务模块，也不依赖具体实现。它只能从 `packages/shared` 各域的 `values.ts` 精确子路径引入确需共用的基础业务取值及取值常量，不引入 DTO、完整业务对象或业务规则。避免把全部能力汇成万能接口或退化为 `unknown`、任意字符串的无类型调用。
- **技术 Adapter** 实现 Platform 的 SSH/SFTP、远端执行、文件、加密、SQLite Runtime、Guacamole、网络等契约，不反向导入业务对象；**业务模块 SQLite Adapter** 实现所属模块内的存储契约，负责本模块 SQL、行解码、引用约束及语义化事务，不放入 Platform。只有确实存在具体技术边界的能力才需要独立 Adapter，不增加空转层。

有多步原子性、资源所有权或重试语义的任务由对应业务模块的存储契约或通用 Platform 能力契约表达为一次完整操作，具体 Adapter 持有事务、连接或句柄；Model 不靠连续调用普通方法拼接原子操作。外部通知和其他不可回滚副作用在成功提交后由原业务 owner 处理。能力入口在安装前、关闭后明确失败；是否采用全局入口由生命周期决定，不能把请求级或 Run 级可变状态放进进程全局变量。

凭据加解密是当前明确的职责例外：Service 持有业务凭据保护规则并调用 Platform SecretBox，Model 只转换已保护的命令与密文快照。通用加解密实现不获得 Targets 类型，也不新增集中式业务凭据组件。

这里的 Backend 业务模块 Model 是应用到基础能力的转换入口；下文 `packages/shared` 中的 `model.ts` 只表示前后端共用的业务对象与纯规则，两者职责不同。

### 逐模块迁移范围

| 顺序 | 基础能力                                 | 首要边界与需要保留的 owner                                                                                                                      |
| ---- | ---------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| 1    | SQL 存储、迁移与事务                     | 所有现有 Repository 和 SQL 消费者迁至模块 Model → 本模块存储契约 → SQLite Adapter；多表提交由存储 Adapter 原子执行。细节见下文。                |
| 2    | SSH 连接、命令执行与远程文件系统         | 连接/Workspace/Agent 各自将目标与凭据转换成 Platform 的连接请求；SSH Adapter 持有底层连接和 channel，使用方持有会话或文件句柄的关闭责任。       |
| 3    | 加密、密码散列、Passkey、双因素与验证码  | 各业务模块保留凭据规则和授权；Platform 定义密码学或外部验证能力，Adapter 持有 Node/第三方实现及密钥运行时。明文与密钥不进入公共日志或共享 DTO。 |
| 4    | 通知与外部通信                           | 通知模块决定收件人与发送时机，Model 转换发送任务；Platform 定义投递结果与失败语义，渠道 Adapter 实现 SMTP、Webhook 等网络调用。                 |
| 5    | 传输、归档、Docker、浏览器与远程桌面     | 保留现有任务/会话 owner；Model 转换应用任务，Platform 约束流、取消、背压和资源释放，Adapter 隔离具体协议与库。                                  |
| 6    | Agent Provider、MCP、Plugin 与执行集成   | 保留 Run、授权、审批、lease、Plugin 生命周期 owner；只把外部 Provider/协议/进程能力放入 Platform 契约，不把 Agent 状态机下沉为通用基础组件。    |
| 7    | 系统信息、诊断、会话文件、备份与外部资源 | 按实际调用链补齐 Model 与 Platform 边界；进程采集、文件、远端服务由 Adapter 实现，诊断与备份的业务编排仍归原 owner。                            |

每处理一项，先列出当前调用方和生命周期，再确定该能力的 Model 输入/输出、Platform 契约、具体 Adapter 与 Bootstrap 安装点；同时迁移该项全部消费者，验证其公开行为、错误、取消、恢复及资源清理，最后移除旧端口、重复格式转换与装配代码。已有正确边界可保留，不为四层形式增加空转代码。下文的共享类型与 SQL 设计适用于全局；连接和 Agent 只是第一项的示例，不限定迁移范围。

## Backend 顶层业务模块划分（规划，第一版仅施工 Targets 切片）

顶层模块依据**业务数据 owner、运行生命周期和跨模块消费者**划分，不按旧包目录、路由数量、独立 Service 个数或注册粒度拆分。未来新后端业务模块固定为以下八个方向（尚未实施的目录不创建空占位）：

| 顶层模块        | 内部功能与边界                                                                                                                                                                                | 数据及生命周期 owner                                                                           |
| --------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------- |
| `access`        | 用户、登录/会话、密码、Passkey、2FA、验证码、IP 黑白名单                                                                                                                                      | 谁可以进入系统；Auth/Session 的唯一 owner                                                      |
| `targets`       | SSH/RDP/VNC 连接配置、凭据、Proxy、SSH Key、标签、导入、目标解析、配置指纹、连接测试                                                                                                          | 连接到哪里和使用什么配置；内部 Proxy/SSH Key/Tag 可以独立管理、独立注册，但不是顶层模块        |
| `remote`        | `sessions /` SSH 终端、挂起/恢复、RDP/VNC 会话；`files /` 浏览/编辑/上传/下载；`transfers /` 跨服务器任务；`operations /` 远端命令/Docker/状态监控；`history /` 快捷命令、路径/命令历史与收藏 | 对远端做什么；Session、Transfer 与 RDP/VNC ticket 分别持有自己的生命周期，互不作为附属 Service |
| `agent`         | 对话、Provider、Run/StateCommit、审批/协作/Subagent、Memory、工具/策略、Plugin/MCP/ACP、Artifact、Agent SSH 与后台任务                                                                        | Agent 授权、durable 状态、执行、恢复的唯一 owner                                               |
| `preferences`   | 通用设置、Workspace 布局/显示偏好、外观、背景、HTML/终端主题                                                                                                                                  | 用户界面配置；运行中的 Workspace 会话不归这里                                                  |
| `notifications` | 通知配置、事件格式化、邮件/Telegram 等渠道投递                                                                                                                                                | 多业务事件的投递策略、队列与消费生命周期                                                       |
| `audit`         | 审计记录和查询                                                                                                                                                                                | 跨模块写入，独立数据与读取入口                                                                 |
| `system`        | 健康诊断、备份恢复、数据库管理编排                                                                                                                                                            | 管理性操作与全系统停机协调；恢复前协调 Agent、Transfer 和 SSH 会话                             |

`remote` 是产品功能容器，**不是共享巨型 Service**。SSH 终端 Session、Transfer Orchestrator、Remote Desktop Session 分别管理连接和任务的创建、取消、恢复与关闭，目录相邻不合并生命周期。前端现有 `filesystem`、`file-editor`、`file-preview`、`terminal`、`docker`、`status-monitor` 可继续按 UI/功能消费组织，不机械复制后端结构。

`targets` 为 Agent/Remote 提供目标配置、引用和指纹的公开能力；Agent 持有自己的授权和 Agent SSH 会话，`remote` 持有远程任务与终端/文件会话；真正的 SSH、SFTP、远程执行、SQLite、加密、Guacamole 和网络投递为 `platform` / 技术 Adapter，不定义 Connection、Agent 或 Workspace 的业务对象。Shared 按两端确实一致的取值、业务和协议语义分域，不按技术目录组织。

模块的内部 `register.ts` 可以细分 Proxy、密钥和 Tag 子功能；只有 `bootstrap/module-manifest.ts` 中的一级条目才代表独立业务模块。后续审查迁移时同时检查 Backend Service、HTTP/WebSocket、Frontend Feature 和 Bootstrap 消费者；不要根据旧命名反推 owner。

## 前后端共享类型重构（待实施）

### 包与依赖边界

将现有所有前后端共享类型与少量纯规则收敛到 `packages/shared`，包括 `packages/protocol` 的公共契约和目前散落在前后端的重复业务取值；完成消费者迁移后删除 `packages/protocol`。`shared` 同时承载前后端含义一致的基础取值与业务对象，以及 HTTP、WebSocket 的请求、响应和事件契约；按业务域组织，域内再区分 `values.ts`、`model.ts`、`api.ts`、`events.ts`，不建立一个全局大类型文件。

```text
packages/shared/src/
  connections/
    values.ts      # ConnectionType 等有限取值与取值常量
    model.ts       # 双方共用的业务对象与纯规则
    api.ts         # HTTP 请求与响应
  agent/
    runs/
      values.ts
      model.ts
      api.ts
      events.ts    # WebSocket 事件
    approvals/
      ...
  workspace/
    values.ts
    model.ts
    api.ts
    events.ts
  common/
    api.ts         # 少量真正跨域的契约
```

目录按业务 owner 和实际消费者增减文件：没有共享取值的域无需 `values.ts`，没有事件的域无需 `events.ts`，大型 Agent 域按 Run、审批等能力拆分；Proxy、SSH Key、Tag 即使与 Connections 关联，也分别放在自己的业务域。`values.ts` 只导出有限取值类型及其取值常量，不放业务对象、应用模块类型、API 字段结构或业务规则。`model.ts` 只放前后端语义和字段确实一致的业务对象或纯规则；`api.ts` 放请求/响应 DTO 与边界校验，`events.ts` 放事件载荷。依赖只允许 `values.ts` → 无同域依赖、`model.ts` → `values.ts`、`api.ts`/`events.ts` → 本域 `values.ts` 或 `model.ts`，避免反向导入和域间循环。跨域公共文件只收纳确有多个域消费且语义相同的契约，不把类型搬进 `common` 以绕开 owner。

包的 `exports` 显式列出确实存在的精确子路径，例如 `@nexus-terminal/shared/connections/values`；不通过根入口或通配符汇总所有业务域，也不为尚未实现的域创建空文件或兼容别名。Frontend 和 Backend 只能从这些公开子路径引用 Shared，不深入引用 `src` 文件。`shared` 不依赖 Backend、Frontend、数据库、HTTP 框架或 Vue，只包含两端均可安全使用的类型、常量、纯函数及必要的运行时校验规则。

### 类型归属与转换

以连接类型为例，`shared/connections/values.ts` 唯一定义 `ConnectionType = 'SSH' | 'RDP' | 'VNC'` 及需要复用的取值常量；同域 `api.ts` 的 `ConnectionDto.type`、Backend 连接业务对象和 Frontend 表单引用该类型。连接类型表示基础业务取值，不归 SQL 层或 API DTO 独占，也不与完整连接对象混放。现行 protocol 与 Backend 各自定义的相同字符串联合类型在迁移后只保留这一份。

API 请求、响应与事件的字段结构留在 `api.ts`、`events.ts`；`Dto` 后缀仍可用于标识网络数据结构。Backend 的加密凭据、存储命令、事务状态与 SQLite 行类型留在 Backend；Frontend 的表单、组件和展示状态留在 Frontend。相似但语义不同的类型不强行合并。也不从大型业务对象用多层 `Pick`/`Omit` 自动生成全部 API 或持久化类型；边界结构应清楚表达公开字段与敏感字段。

Frontend/Backend 复用 TypeScript 定义不代表网络或数据库数据可信。HTTP 与 WebSocket 入参在边界从 `unknown` 校验；SQL 存储结果由应用侧 `sqlModel` 在转换时校验，数据库列按需要设置约束。没有实际表示差异的字段直接传递；确有差异时只在所属边界做一次明确转换。`shared` 不承载 SQL 行映射、凭据解密或前端 UI 适配。

### 迁移顺序

每重构一个类型，先查旧 Backend、`backend-next`、Frontend、`protocol` 的定义及实际引用，并在本次功能方案列出 owner、前端消费者、Backend 消费者、运行时表示与目标文件。只要双方消费同一语义与表示，就把**唯一定义**移到 Shared，并在该功能迁移步骤更新双方全部引用；Frontend `model` 或 `public` 可按本模块边界转导，但不能再声明另一份联合类型或 DTO。若只是名称相同而表示不同，例如旧 API 的 `route: null` 与新存储的 `route: 'direct'`，保留分别命名的边界类型和显式映射，不把两者伪装成同一个共享类型。仅单端消费的类型留在该端。

先盘点当前功能真正使用的类型，再随每个功能增量按域迁移；未用到的域暂不搬迁，也不预先复制整个 `protocol`。连接与 Proxy 的有限取值已进入 Shared；SSH Key、Tag 和 API 类型随相应功能接入，顺序见[下一阶段实施方案](后端重构下一阶段实施方案.md)。每个迁移域收口时复查其前端组件、store、API 客户端、跨功能 `public`、旧 Backend、`backend-next` 与 `protocol` 引用，确认该域没有同义重复定义或漏掉的消费者；HTTP/WebSocket 边界仍要校验真实数据。所有消费者切换完成后删除 `packages/protocol`、旧导出和失效引用，不保留双包兼容入口。

## SQL 存储架构设计（第一版 Targets 连接存储切片施工中）

### 总体结构与归属

Bootstrap 按应用实例创建 SQLite Runtime、初始化 schema version，再通过模块 manifest 注册各业务模块。Platform 只拥有 SQLite Worker、排他事务队列、参数绑定和数据库生命周期等**通用机器能力**，不拥有 Connection/Proxy/Tag/Agent 等业务存储数据、契约或注册槽位。业务存储契约与记录位于所属模块。

```text
Bootstrap → Platform SQLite Runtime → schema version → targets schema → registerTargets
Targets Connection Service → Connection Model → Targets 内 ConnectionStorage → SQLite Adapter
Targets Import Service ────→ Connection Model → Targets 内 ImportStorage → SQLite Import Adapter
                                                              └→ 显式 tx → Connection/Proxy/Tag SQL
Remote / Agent 业务用例 → targets/public.ts 的窄目标能力 + Platform SSH/SFTP/执行能力
```

### 当前 Targets 凭据与迁移

Platform 的 `schema.ts` 现在接收按编号的 `SchemaMigration[]`：其职责是验证版本历史、在每号独立事务中执行模块迁移并写入同一事务版本 marker。Targets 的 `migrations.ts` **当前只注册完整 v1 初始结构**；连接/代理/标签、Proxy/Tag `version`、加密 SSH Key、连接认证关联和 Proxy 密文表均由所属子功能的一版建表 SQL 创建。原 v1→v2 只用于未发布开发阶段的真实迁移/回滚测试，验证后不保留 v2 生产入口。`schema_version` 带签名，旧原型 v1 数据库将明确拒绝启动，避免同版本不同表结构被误认成兼容数据。SQL Runtime/Worker 不获得 Connection 或 SSH Key 业务类型；应用实例的加密能力由 `platform/security/secret-box.ts` 提供 AES-256-GCM，启动方必须显式传入 32 字节主密钥，代码不内置默认密钥。

Targets 的 Proxy、Tag、SSH Key 均已有真实的管理 Service/Model/存储契约与 SQLite Adapter；按实际业务复核后没有把旧 Proxy 私钥、旧路由 JSON 或旧认证字段无差别带入新表，RemoteApp 仅允许 RDP 配置；连接密码与 SSH Key 选择通过独立 ConnectionCredentialService 以 CAS 在 SQLite 事务内写入。Proxy/SSH Key 的数据库存储只含密文、公开列表和详情不返回凭据。引用与修改的保护由 SQLite 外键和写事务检查承担；代理、密钥的机器配置修改影响被引用 SSH 目标指纹，展示名称、备注、标签以及普通 CAS 版本不改变指纹；跳板链禁止环路和过深引用，克隆连接应同时克隆认证配置。

`targets/resolver` 的 SQLite 查询在单个事务快照中读取主连接、Proxy、SSH Key、凭据与全部跳板，Model 将密文快照转换为独立应用类型，并根据同一次读取中的机器配置、引用身份、密文及有序跳板生成 SHA-256 指纹，不包含普通 CAS 版本。Resolver Service 调用通用 SecretBox 解密并组装机器 SSH 连接参数；各写入 Service 负责加密。Model 不接收 SecretBox，不负责加解密，也不把存储类型作为 Service 的入参或返回类型。**解密结果只能在受信 Backend 内部的 `trustedSshTargets` 能力中传递**；普通 `targets` 管理接口只暴露非敏感连接、代理、标签和密钥摘要，不提供任何 HTTP/WS 接入。未来 Access 完成真实认证/授权后才接入 Targets HTTP，届时同步移动前后端共享 DTO、前端 API/Store，并在 API 边界转换旧 `route:null` 与新 `direct`。正式 SSH 网络建连、Remote Session/Transfer 与 Agent 持久状态仍属于后续各自阶段，没有假实现。

### 存储契约、模块装配与事务

`modules/targets/connections/storage/connection-storage.ts` 持有连接 CRUD、CAS 与元数据存储记录；`modules/targets/import/storage/import-storage.ts` 持有单条导入语义化存储契约；`modules/targets/proxies/storage/proxy-storage.ts` 持有导入所需代理数据。Connection Model 与 Import Model 分别接收本实例的只读 `ConnectionStorage` 和 `ConnectionImportStorage`，而不是 SQLite Runtime、Platform 注册表、完整业务数据库或通用 SQL 接口。Service 使用各子功能 `model/*-types.ts` 的应用类型，Model 输入和返回值独立于存储契约；字段表示相同时也逐字段构造存储命令和应用快照，列表、补丁、联合状态和嵌套对象同样转换。SQLite Adapter 做物理行解码，Model 按用例需要校验应用不变量。连接凭据的明文输入不放入 `storage/`，存储契约只接收密文或 Key 引用。

`modules/targets/register.ts` 负责装配 Connection SQL Adapter、Import SQL Adapter、Connection Model、Connection Service 与 Import Service，返回经过显式投影的管理 `publicApi` 及独立的可信解析能力；不会在注册文件中执行 SQL。普通 CRUD SQL 在 `connections/adapters/sqlite`，Proxy/Tag 的 SQL 与建表语句也各自在自己的 `adapters/sqlite` 下。Targets 的 `migrations.ts` 将 Proxy、Tag、SSH Key、Connection 和认证关系依外键顺序装配为单一 v1 Schema；`schema.ts` 只对 Bootstrap 转导清单。唯一单条导入事务 owner 是 `import/adapters/sqlite/import-sql.ts`：使用 Platform Runtime 的 `transaction(work)`，向 `ImportTransactionParticipants` 中连接、Proxy、Tag 的函数传递**同一个显式 `tx`**。注册文件把具体实现注入该端口，Import Adapter 不直接深层导入其他子功能的 SQL，也不通过 Service/默认连接重新开启事务。外键/关系失败回滚整条导入，多条按记录分别提交；审计后续在提交后执行。

应用关闭由 Bootstrap 负责该 SQLite Runtime 的拒绝新操作、drain、关闭；进程内不同 DB 路径的实例彼此独立，禁止重复打开同一规范化路径。字段、SQL、表名仍只在业务 SQLite Adapter 和 schema 中；动态更新只采用固定白名单及绑定参数。当前已包含密文凭据存储与目标解析，但尚未接入 HTTP/认证、Agent、SSH 网络及 Remote Desktop ticket。

### 当前仍需收口的边界

- **模块错误出口尚未转换。** `import/service/connection-import-service.ts` 把捕获的异常直接 `String(error)` 放入逐条导入结果；`public-mappers.ts` 只复制该字符串，其他管理方法也直接传播底层异常。字段白名单已隔离内部对象，但不能隔离错误正文里的 SQLite 表名、约束等实现细节。需定义 Targets 拥有的安全错误码/结果，模块出口映射可预期失败；未来 HTTP 层再转换为协议与本地化提示，未知内部异常不能透传正文。
- **SQLite 失败后的生命周期契约需要补齐。** `platform/storage/sqlite/sqlite-runtime.ts` 吞掉 ROLLBACK 的失败，没有把无法确认事务状态的实例标为不可继续使用；`close()` 的重复调用等待队列而非完整关闭 Promise，且事务回调内调用 `close()` 会等待自身事务。接入 Agent 前需明确提交结果未知、回滚失败后的不可用状态，以及共享关闭 Promise 和禁止事务内关闭；不能自动重放未知提交。
- **跳板图约束需要统一。** Connection 写入的递归 SQL 允许 16 条引用边，Resolver 的 `path.size >= 16` 则把主目标也计入节点上限，可能保存成功但解析失败。写入只从被修改的节点复验深度，延长该节点的链也可能让已有祖先目标超过限制。需要由 Targets 明确定义跳数、深度与总解析规模的含义；SQLite 写事务复验受影响的祖先，Resolver 使用相同约束，不能依赖遇到递归错误才拒绝。

这些项尚未修复；当前无正式 HTTP/SSH/Agent 接入，不能将本轮静态审核视为完整运行验收。Proxy/SSH Key/Tag/连接凭据的 Model 转换边界和模块正常结果出口已经落实，不再作为开放问题。

### 后续模块边界

Targets 后续负责安全连接/标签/代理/SSH Key 管理、目标解析、配置指纹、连接测试及 RDP/VNC **连接定义**，但不持有 SSH 会话、远程桌面票据、跨服务器传输任务或 Agent grant/审批。Remote 负责独立的 sessions/files/transfers/operations/history 子能力与各自资源生命周期；Agent 保留 Run、权限及恢复。Preferences 管布局和外观持久数据而非远程会话；Notifications/Audit/System 各自负责投递、审计、维护协调。共享有限取值如 `ConnectionType`、`ProxyType` 留在 Shared 的精确子路径。

### Agent 存储接口

Agent 模块在自身目录定义按职责划分的对话、Memory、配置、Plugin、Run 等存储契约；Agent Service 把要推进的状态交给本模块 Model，再调用模块内的语义化状态提交接口。一次提交在同一个显式 SQLite 事务中读取最新持久状态、执行 Agent 拥有的状态决策、检查版本及其他前置条件，并原子更新 Run、步骤、Tool、审批、事件及幂等记录中相关的部分。事务内存储参与者属于 Agent 模块；Platform 只提供通用 `transaction(tx)`，Model 不直接获取通用 SQL 执行器。

Run 快照和事件读取与状态提交分开。Agent Service 发起状态转换；Agent 模块拥有业务决策与应用映射，SQLite 实现负责事务内读写及持久化条件校验；提交成功后的调度、通知和外部资源清理由 Agent owner 根据转换后的提交结果处理。Agent 的运行时状态不能拆成多个独立的表级全局调用。预先生成提交计划再以多对象版本条件写入是可选方案，实施前须证明其并发条件完整，不作为当前默认前提。

### 初始化、事务与生命周期

Bootstrap 为每个应用实例创建并初始化 SQLite Runtime，完成模块 schema 初始化，并调用各业务模块 `register` 创建只读存储能力与公开用例，最后启动 HTTP、WebSocket 和 Agent 调度。关闭和数据库重置由同一实例生命周期 owner 管理；关闭后的存储调用明确失败。同一规范化数据库路径不得被同进程的两个应用实例同时打开。

普通操作由各域 Model 调用该模块构造时接收的只读存储契约；跨多表、跨子功能的原子操作由对应模块的语义化 `commit` 方法持有完整事务。事务内所有读写使用同一事务连接，不通过默认入口执行，也不依赖隐式异步上下文切换事务。数据库提交完成后才发布外部事件或执行通知。

### 实施边界

盘点全部现有 SQL 消费者，按业务域替换数据访问入口，避免 Repository、Model、Adapter 长期并存为重复调用链。SQL 方言及原始 SQL 字符串只留在 `sqliteAdapter`；应用对象与存储内部类型的双向转换归各域 `sqlModel`，数据库行与存储内部记录的物理映射归 `sqliteAdapter`。验证覆盖各域现有持久化行为、跨表事务和恢复；连接 CRUD 与导入回滚、Agent Run 与审批并发提交是重点样本，不代表全部迁移范围。设计落地前不将本节描述为现行架构。

### 第一模块代码审核：SQL 存储

现行 Bootstrap 的 `composition-root.ts` 实例化大量 SQLite Repository，再逐个传给业务 Service；`compose-agent.ts` 继续接收底层 `RelationalDatabase`，自行构造 Agent Repository 与 StateCommit。`DatabaseAdapter` 通过一个 Worker 和排他队列保证事务内操作不被普通查询穿插；它拒绝嵌套事务。现有事务所有权和业务类型跨层情况如下，重构不能仅改类名或移动文件。

| 范围                           | 现行结构与风险                                                                                                                                                                                              | 新结构必须满足                                                                                                                                                                                                                                                                                    |
| ------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |

连接导入目前接受旧格式 JSON，而当前新格式解析使用类型断言。第一版新后端不兼容旧导入格式，只在输入边界严格校验新版格式，生成应用导入计划；实施时同步更新正式需求和相关 E2E。备份和 Agent App Storage 等涉及任意持久化 JSON 的路径同样需要有界解码，不靠 TypeScript 行类型或 `JSON.parse() as T` 声称数据已验证。

第一版代码范围已在 `packages/backend-next` 实现：Shared 有限取值、SQLite Runtime、真实 SQL/事务、Schema、Bootstrap/Targets 模块组装，以及 Connection Service → Model → Targets 内部存储契约 → SQLite Adapter 的元数据 CRUD 和跨 Proxy/Tag 导入事务。未执行本轮测试，验收待收口；下一批施工及验证安排见[后端重构下一阶段实施方案](后端重构下一阶段实施方案.md)。凭据、Proxy/Tag/SSH Key 管理与目标解析已在第二批实现；审计、结构化日志、Auth/Session、SSH 测试、远程桌面与 Agent 等上层能力按各自 owner 重建。

### 需要先讨论的边界

- **Agent 的事务内状态决策。** 采用 Agent 模块拥有的状态规则和事务内存储参与者，在 Platform 的同一个显式 `tx` 中读取最新状态、决策并写入；应用 Model 不直接获取 SQL 执行器。事务回调不能等待外部资源。预生成计划是可选优化，使用前必须逐项证明 Run、App、Thread、Approval、Subagent 和幂等记录的并发约束。
- **数据库管理操作。** Schema/migration、E2E 重置和整库备份/恢复没有普通应用对象，也不适合通过每个业务模块的 `sqlModel`。建议由 Bootstrap/Backup owner 使用独立的 Platform 管理契约；只让普通业务读写遵循 Service → Model → `sqlAdapter`。这需要作为四层规则的显式例外确认。
- **实例边界已定。** `createBackendApplication` 是可调用的工厂，恢复/E2E 重置也会改变数据库状态；采用应用实例作用域的能力入口，不使用进程级单例，业务模块仍不逐个注入具体 SQLite Repository。
- **损坏持久数据的处理。** 连接 JSON 当前失败时静默退为 `null`，Agent durable decoder 多数失败即报错。严格解码能暴露损坏但可能改变旧数据的读取结果；迁移时按已发布数据格式和恢复要求确定是否需要一次性修复，不能保留无期限的静默默认值。
