# 项目开发入口

本文串联人工规则、AI 工程经验、架构、编码规范和任务；不在这里复制规则列表或业务架构。`USAGE.md` 持续维护实际产品行为，本轮不清除其现有需求与使用说明。开发前必须读取并理解适用文档，再查看代码和开始修改。人工要求统一以 HUMAN.md 的 8 条规则为准，工程经验和设计分别由对应文档维护。

## 开发前必读

按以下顺序读取；不能只读目录、标题或依赖上次任务的记忆。

1. [人工规则](rules/HUMAN.md)：完整读取，严格执行。
2. [AI 工程经验规则](rules/ENGINEERING.md)：完整读取，核对已知问题类型。
3. [编码规范](rules/CODE_STYLE.md)：完整读取，包括封装、命名、控制流和格式。
4. [模块设计模板](architecture/MODULE_TEMPLATE.md)，以及任务涉及的 [后端](architecture/BACKEND.md)、[前端](architecture/FRONTEND.md)、[Shared](architecture/SHARED.md) 架构。
5. 当前功能对应的 [产品行为](USAGE.md)、[实施任务](后端重构下一阶段实施方案.md) 和 [验证入口](testing/E2E.md)；部署工作另读 [部署](DEPLOYMENT.md)，远程桌面另读 [专题架构](architecture/REMOTE_DESKTOP.md)。

理解后，在本次工作说明中简要指出真实 owner、允许依赖、类型转换位置、消费者和完成判据。缺失的设计先按模块模板补齐，不能靠随意建目录或复制旧模块决定新架构。

## 文档分工与优先关系

| 入口                   | 唯一内容                                | 更新责任                |
| ---------------------- | --------------------------------------- | ----------------------- |
| `rules/HUMAN.md`       | 项目所有者明确提出的规则                | 仅按人工输入更新        |
| `rules/ENGINEERING.md` | 已确认问题提炼出的可复用开发规则        | AI 随修复和工程演进更新 |
| `rules/CODE_STYLE.md`  | 封装、命名、函数、类型、错误和格式      | 随代码规范决策维护      |
| `architecture/`        | owner、目录、依赖、契约、事务与生命周期 | 设计/实现边界变化时同步 |
| `USAGE.md`             | 用户可见行为与限制                      | 功能或行为变化时同步    |
| 实施方案               | 当前未完成任务、依赖与阶段完成条件      | 按实际进度维护          |
| `testing/`             | 命令、覆盖、风险与执行证据              | 按真实验证结果维护      |
| `DEPLOYMENT.md`        | 构建、部署、配置及升级                  | 部署流程变化时同步      |

人工规则优先于其余规则。AI 规则、编码规范和架构按职责相互配合；出现冲突先核对真实 owner 与证据，再更新原条目，不自行发明架构例外。源码偏离规则是待修问题，不能直接把文档改成允许偏离。

## 开发与收口流程

以下是每次开发、重构与审查的总流程。细节按链接维护在对应文档，不能只遵守其中一个阶段。

| 步骤              | 必须完成的工作                                                                          | 详细入口                                                                                       | 本步产出                                                  |
| ----------------- | --------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------- | --------------------------------------------------------- |
| 1. 读取与理解     | 按必读顺序理解约束，查看工作区、当前任务和真实代码；保留既有未提交工作。                | [人工规则](rules/HUMAN.md)、[工程经验](rules/ENGINEERING.md)、[编码规范](rules/CODE_STYLE.md)  | 明确适用规则和任务范围，不凭记忆开工。                    |
| 2. 核对产品行为   | 查 USAGE 对应功能，确认本版新增、变更、限制及失败/恢复结果；文档与源码矛盾时定位事实。  | [每版产品行为维护](USAGE.md#每版产品行为维护)                                                  | 本版行为及需要更新的章节，不擅自删除现有需求。            |
| 3. 明确设计       | 定 owner、目录、依赖、类型、公开入口、事务、资源和消费者，按固定八节模板补齐设计。      | [模块模板](architecture/MODULE_TEMPLATE.md)、对应架构                                          | 可审核的功能归属和边界；已实现与计划明确区分。            |
| 4. 分阶段规划     | 列真实消费者、缺口、依赖、源码和行为判据；每阶段写检查命令，不把检查推迟到末尾。        | [任务组织与阶段门禁](后端重构下一阶段实施方案.md#任务组织与阶段门禁)                           | 可执行的阶段任务，未实施/未验收能力不隐藏。               |
| 5. 实现并同步     | 在真实 owner 修改，同步全部消费者、协议、出口和 USAGE；类型、权限、失败和关闭一起实现。 | [编码规范](rules/CODE_STYLE.md)、[Shared](architecture/SHARED.md)                              | 一致的代码和当前版文档，无重复规则与兼容残骸。            |
| 6. 架构与代码审核 | 对照人工、工程经验和模板检查依赖、类型、SQL、晚到任务、精简性及失败路径。               | [工程经验规则列表](rules/ENGINEERING.md#规则列表)、[模块模板](architecture/MODULE_TEMPLATE.md) | 发现问题先修 owner；新经验按分类更新原条目。              |
| 7. 检查与验收     | 执行适用类型/ESLint/格式/build，失败先修复；按授权运行行为验证，记录未验证范围。        | [阶段检查](rules/CODE_STYLE.md#阶段检查)、[E2E](testing/E2E.md)                                | 真实命令/范围/退出结果，源码与行为完成分别判断。          |
| 8. 文档与交付收口 | 核对本版 USAGE、架构、任务和验证证据一致；关闭已解决项，保留真实缺口。                  | [每版产品行为维护](USAGE.md#每版产品行为维护)、[经验维护](rules/ENGINEERING.md#随工程演进维护) | 可审查改动、完成情况及剩余任务，提交/推送按当前用户指令。 |

每版变更都必须检查 USAGE。用户操作、输入输出、限制、权限、失败或恢复行为变化时，在同一版更新原功能章节；仅内部重构且行为一致时无需机械改写，但必须确认现有说明仍真实。USAGE 不存提交日志，需求设计、已实现能力和待验收状态明确区分。

代码阶段收口执行 `pnpm run check`、`pnpm run format:all:check`、`git diff --check` 和适用包 build。新后端单独执行 `pnpm --filter @nexus-terminal/backend-next check`，根 check 不替代它；Shared 修改同步 Shared check/build 与双端消费者检查。文档任务执行文档格式、链接及 diff 检查。明确环境阻断保留未完成状态，不能把失败推迟到最终阶段后仍宣称阶段完成。

提交范围只包含本任务已审查内容，未知工作区修改不代为提交。测试执行和提交/推送遵循当前任务授权；未执行验证不写成通过。
