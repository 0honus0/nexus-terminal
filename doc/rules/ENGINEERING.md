# AI 工程经验规则

本文将开发和审核中确认的问题提炼为长期规则；不是人工规则、逐次审查日志或完成报告。开发前完整读取，适用条目必须执行；与 [人工规则](HUMAN.md) 冲突时修正本文，不修改人工条目。

## 规则列表

| 编号 | 适用范围       | 规则                                                                                                         | 核对方法                                                                                   | 问题依据                                                              |
| ---- | -------------- | ------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------ | --------------------------------------------------------------------- |
| E-01 | 分层与应用资源 | 审核对象实际暴露的能力，技术连接、lease、channel、Stream 封装在技术转换的 Model/Adapter 内，不交给 Service。 | 沿 Model 返回值到 Service 的完整链路检查字段、方法和关闭职责，不只看目录或调用是否仅透传。 | Files 的应用资源曾包含 Machine/SFTP 句柄。                            |
| E-02 | 类型归属       | Service、Model 和模块内部协作引用唯一应用类型 owner；Model 不反向依赖 Service，公开签名不借用私有类型。      | 对用例输入、结果、联合状态逐一定位定义及消费者，确认跨边界转换 owner。                     | 内部类型反向引用上层、安装配置和公开关闭原因曾引用私有类型。          |
| E-03 | Shared 完整性  | 审查所有已经实现的通信功能，而不只是已有 Shared 目录；协议、对象、基础取值、错误和容量与双端消费者同步迁移。 | 列出实际 HTTP/WS 端点、后端出口、前端 API/解码和 package exports；缺任一环节列为开放任务。 | Agent 已有状态 HTTP，但 Shared Agent 与新前端消费者均未迁移。         |
| E-04 | SQL 与迁移     | 业务 CRUD、DDL、模块迁移、技术版本表、PRAGMA 和事务控制均核对 Adapter 归属。                                 | 模块迁移只调用初始化接口；核对 SQL 下移后安装顺序、同一事务和版本签名。                    | Agent migrations、Host Key schema 及技术迁移/事务控制曾直接携带 SQL。 |
| E-05 | 异步等待       | 超时或 Promise.race 只结束等待；晚到 resolve 与 reject 都由原资源 owner 追踪收敛。                           | 逐条检查准入名额何时归还、成功资源如何关闭、拒绝中的清理失败如何进入有界诊断和停机汇总。   | Files 追踪了晚成功，却忽略晚拒绝中的半开清理失败。                    |
| E-06 | 清理与失败     | 正常授权/建连拒绝与清理完整性失败具名区分；原操作和清理同时失败保留全部因果。                                | 检查创建、二次身份复核、登记、操作和关闭各失败分支；不靠错误文本分类。                     | Files 与 PTY 创建失败后的清理证据可能未进入停机结果。                 |
| E-07 | 状态与竞态     | await 后重新读取权威状态，终态不再操作或发布旧资源；类型错误通过状态设计解决。                               | 检查授权、I/O 和关闭等待后的保护，不删除 fence、增加断言或放宽类型换绿。                   | PTY 局部状态缩窄引发 TS2367，必要终态保护必须保留。                   |
| E-08 | 类型与常量     | 同义同表示的双端取值归 Shared；私有配额、缓存和清理策略留真实 owner，不因是数字就升为协议容量。              | 核对语义及真实消费者，区分完整 wire 字节预算、产品限制和技术内部限额。                     | 文件种类重复定义；私有关闭重放等常量曾放在 Shared。                   |
| E-09 | 封装与转换     | 跨边界白名单转换保留；同一边界只保留一个转换 owner，包装必须提供实际隔离或语义。                             | 核对 mapper 输入/输出所保护的边界，删除重复 mapper 与无消费者别名，避免万能 mapper。       | mapper 职责混淆、重复投影和空转 Model 容易掩盖类型边界。              |
| E-10 | 阶段完成       | 源码实现、静态检查和行为验收分别判断；已知失败必须在当前阶段解决。                                           | 记录命令、范围、退出结果和 SHA/工作区；环境恢复后替换历史阻断说明，待验专项不误关闭。      | 类型和格式失败曾被“源码已完成、只待环境验证”掩盖。                    |
| E-11 | 资源保证       | 本地取消、destroy、退役和关闭请求不证明远端操作停止或副作用回滚。                                            | 分别说明本地资源终态、远端 unknown、整体停机期限；路径检查不冒充原子 nofollow 或内容快照。 | SFTP 与异步关闭中的技术保证容易被描述成完整产品保证。                 |

| E-12 | 版本与产品文档 | 每版变更核对 USAGE，对行为变化同步更新原功能章节；架构重整不清除仍有效的产品说明。 | 核对用户流程、权限、输入输出、容量、失败/恢复及已实现/待验收标记；纯内部重构确认行为一致。 | 文档规则重整容易误删产品事实或让需求与实际版本脱节。 |

## 随工程演进维护

发现问题先确认调用链、真实结果和根因，再决定修复及可复用约束；不能把假设直接写成强制规则。现有类别优先更新原条目，新类别追加固定编号。规则必须有适用范围、核对方法和简短依据，不积累提交日志或无消费者的预留约束。

架构改变时同步检查相关经验是否仍成立；失效条目删除，范围变化更新原条目，不长期保留冲突版本。实践产生的新建议只能更新普通规则，不能自动升级为人工规则。规则执行依靠阅读、设计和人工代码审核，使用现有静态工具验证代码，不新建读取源码文本或目录形状的自定义规则门禁。
