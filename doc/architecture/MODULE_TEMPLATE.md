# 模块设计模板

新增模块、子功能或改变边界前，按本文八个章节补齐对应架构设计。章节顺序固定；无相关能力写“不涉及”及原因，不为模板创建空源码目录。设计放入对应架构文档，不另建散落的设计/审查文件。产品行为放 [USAGE](../USAGE.md)，任务与执行结果放实施方案及测试文档。

## 1. 职责与范围

说明功能解决什么问题、数据和状态由谁拥有、使用者是谁；区分当前已实现与设计中的能力。一级模块按业务所有权和生命周期划分，不按表或路由数量划分。

## 2. 子功能与目录

列出子功能、具体目录及职责，明确新增文件放在哪里、复用哪个现有 owner。每个目录说明职责，不随意新建平级能力、杂项目录或空层。复杂纯业务规则可放子功能 `*-rules.ts`，不作为新的调用层；明确 Service 的用例流程、Model 的转换与 Adapter 的事务执行职责。按 E-01.2 标明政策、默认值与各类容量的 owner；通信入口放在所属模块约定的 interfaces，不因新增子功能另建同义入口树。

## 3. 依赖方向

列出允许依赖、实际公开入口和禁止引用；技术契约、实现和业务对象分开。跨模块不深层引用私有实现，同模块协作不绕行公开包装或全局 dispatcher。

## 4. 类型与转换

| 边界             | 输入/输出语义            | 类型唯一 owner                    | 转换 owner                  | 实际消费者           |
| ---------------- | ------------------------ | --------------------------------- | --------------------------- | -------------------- |
| 协议 → 应用      | 明确完整请求与身份来源   | Shared HTTP、模块 Model 类型      | Interface/模块入口 mapper   | 对应端点与用例       |
| 应用 ↔ 存储/技术 | 明确内部命令、记录及资源 | Model、storage、Platform 分别归属 | Model 与技术 Adapter        | 真实调用链           |
| 应用 → 公开/协议 | 明确允许输出的字段       | 模块 public 或 Shared             | public mapper、HTTP/WS 投影 | 后端模块或前端消费者 |

按 E-02.5 核对签名、结果、错误和回调的类型 owner；每个边界注明字段单位、编码及可选/必填语义；同名字段也核对表示是否一致。写命令与只读记录区分，技术与供应商契约按各自 owner 明确转换。按 [人工规则](../rules/HUMAN.md) 填写，不把秘密、存储行、技术句柄放入 Shared。无双端消费者不能声称通信迁移完成；不得只检查已有 Shared 文件。

## 5. 入口与安装

说明公开能力、HTTP/WS 路由、register 配置和 Bootstrap 安装点。业务入口完成权限和用例，协议入口严格解码；模块内部能力不全部对外导出。

## 6. 数据、事务与并发

说明持久化 owner、Adapter、SQL/DDL 和迁移入口、事务边界、版本/幂等/竞争结果。多表写入在真实存储 Adapter 同事务执行；需要当前事实的纯业务判断在同事务内经 Model 转换回调执行，Adapter 不引入规则实现或应用类型，不能把判断移到写事务外。回调使用 storage 类型，由 Model 转换应用事实及决策，不通过装配层注入应用对象。外部副作用不冒充数据库原子性。不涉及持久化时说明状态权威。

## 7. 生命周期与失败

说明资源创建、准入、超时、取消、晚到成功/拒绝、失败汇总、关闭及恢复；区分等待结束、真实任务结束与远端结果。标明首个副作用、实际提交、后续确认、最终交付和释放的完成判据；逐阶段说明取消/失败后谁仍持有资源及由谁恢复，按 E-10.4 核对跨阶段分支。Agent 和普通 SSH 如共用技术能力，分别说明授权与活跃资源 owner。

## 8. 当前能力与验收

列出已实现、尚未实现和已知保证限制；对应 USAGE 章节、真实消费者、静态命令及适用行为判据。未执行检查保留状态，不把设计或编译成功写成产品完成。具体工作列入当前实施方案，避免架构里堆逐次报告。
